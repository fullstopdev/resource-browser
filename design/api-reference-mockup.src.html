Design proposal · EDA API reference

Find the resource, see what you can do, copy the request

Network engineers come to the API reference with a resource in mind: "how do I create a BridgeDomain over the API?" This proposal drops the schema graph and organises all 56 EDA APIs around resources and actions, with a ready-to-run request for each.

Before

Why the current explorer is still hard to use

  1. It speaks OpenAPI, not EDA. 145 paths like /apps/services.eda.nokia.com/v2/namespaces/{namespace}/bridgedomains/{name}/_revs in one list, grouped under a tag called "apps".
  2. You must know which API holds a resource. BridgeDomain is in "Services", BGPPeer in "Protocols", Ping in "OAM". There is no search across APIs.
  3. The same 7 to 9 endpoints repeat for every resource, without saying what each one does (_revs, _targets, _topology).
  4. No ready request. You assemble the URL, the token header and a body yourself.
  5. The schema graph answers a question network engineers rarely ask and carries 38 MB of generated data.

After

Proposed API reference, working example

Search "bgp" or "ping" in the sidebar, open a resource, pick an action. API names, resources, paths and parameters are real 26.8.2 data.

eda-resource-browser.pages.dev/openapi?release=26.8.2&api=services.eda.nokia.com/v2&resource=bridgedomains

      Second pass

      From the reported screenshot to a reference layout

      Feedback: the resource page was not well designed. The action list repeated truncated paths, two heavy scrollbars squeezed the content, the detail stacked boxes and filler text, the curl scrolled sideways, and the example body was a dump of placeholders. The second pass puts the reference beside a dark code rail, keeps only the part of each path that differs, and writes minimal, realistic request bodies.

      What changes

      Implementation outline

      Explorer

      • Overview landing: how to call the API (base path, bearer token, namespaces) and every API as a card with its resources.
      • Sidebar: one search across all APIs and resources, the platform API sections, and each application API with its resources.
      • Resource page: kind, API group, scope, link to the CRD schema, and an action table in plain words (List, Create, Get, Replace, Patch, Delete, History, Intent targets, Topology).
      • Action panel: a curl you can paste (namespace eda, a name, the token as a variable, an example body), parameters, request and response schemas, status codes.
      • Schema graph removed, with its code and 38 MB of generated graph files.

      Data and links

      • A small per-release index (api-index.json) built with the other generated data powers the overview and the search.
      • Resource names come from the CRD manifest, so the API reference and the CRD catalog use the same kinds and link to each other.
      • Old links keep working: ?spec=… and #operationId open the matching resource and action.
      • Compare APIs keeps its layout and links into the new resource pages.
